### 本轮新踩的平台坑（记入防坑）

1. 本 SDK 的 `AppEntity` 要求**嵌套** `DefaultQuery` + 显式 `static var defaultQuery`
   （协议扩展只给 RawRepresentable String 提供默认实现）。
2. `EntityQuery` 必须实现 `entities(for identifiers:)`，仅 `suggestedEntities()` 不够。
3. 弹性语义拆分时若只改 `isDue` 会把进度环分母一起污染——「可打卡」≠「应做」，
   必须两个谓词并存（`isHardDue` 供环/热力图分母使用）。

## 0.45 第八轮：小尺寸组件显示多个习惯（用户反馈），56/56

- 结论先行：iOS 桌面小组件**不支持滚动**（系统限制），「一个小组件里滑着看多个」
  不可行。行业通行做法（HabitKit/Streaks）= 小尺寸锁定单个习惯 + 想看几个加几个。
- 实现：「今日习惯」从 StaticConfiguration 改为 **AppIntentConfiguration**，
  复用习惯格子的 `SelectHabitIntent`——小尺寸长按「编辑」可选定某个习惯；
  未选则自动轮换「第一个该做未完成」。中/大尺寸仍为全量清单（配置项不设即不影响）。
- 回归：test18（含组件库选小尺寸添加 + 组件打卡回写）通过；全套 56/56。

## 0.23 第十三轮：小组件跨天不刷新（用户反馈），66 通过 + 1 跳过

用户反馈：昨天加的小组件今天起床还是昨天的数据，重连手机也没用。

- 根因：快照 JSON 是 App 上次运行时「烤」好的（含当时的次数/应做判定），跨天后
  没有任何东西重写它——组件每 30 分钟重渲染的是同一份过期数据。连手机/解锁都
  不会触发组件刷新（WidgetKit 机制如此）。
- 修复（三层）：
  1. **渲染期跨天重算** `habitsForRender()`：快照不是今天写的时，从 26 周格子
     重推「今天」的次数（新一天格子 r=0 → 归零）、应做判定（格子 due）、弹性
     周进度（本周 done 格计数）；快照是今天的则原样保留精确计数（9/8）。
  2. **打卡 Intent 同步今天的格子**：组件打卡除更新 habits 外同步写今天格子的
     r/due，保证后续跨天重算的数据源正确；Intent 自身也先过 habitsForRender
     （旧快照上打卡不会把昨天的次数带进今天）。
  3. **时间线重载对齐午夜**：nextReload = min(30 分钟, 次日 00:01)，跨天那一刻
     组件主动重渲染。
- 平台说明（已告知用户）：WidgetKit 无实时推送刷新，以上是平台内的最优解——
  跨天自动翻转 + 每次打开 App/点组件打卡即时刷新。
- 回归：新增跨天/弹性周重推单测 2 条；test18（组件打卡 E2E）通过；
  全套 **66 通过 + 0 失败**（test23 按设计跳过）。真机已装。
- 运维教训：真机构建与模拟器全套测试**并行**执行会把模拟器挤挂
  （全部用例 "SBMainWorkspace Busy" 启动失败），必须串行。
- 顺带（用户前一问「连续天数没有加」）：从手机实拉数据库核实——9/16 喝水 8/8
  完成（已计入连击），9/17 6/8 未完成；宽限语义下当天未达标不加但不断链，
  喝满 8 杯瞬间 +1。语义正确非 bug；小组件此前显示旧数据是本轮修复的跨天问题。
